# Yolmod V1 implementation roadmap

**Status:** Authoritative execution order. Every stage remains small enough to implement, test, review, and commit independently.

## Complete

- `FUNCTIONAL-01B` — audit reconciliation
- `FUNCTIONAL-02A` — Turkey vehicle/trust/search contract design

6. `FUNCTIONAL-02D` — replace capped `getHomeListings(60)` browser filtering with server search, URL normalization, pagination, filters, and loading/error/empty UX.
7. `FUNCTIONAL-02E` — migrate Sell/Edit to vehicle and trust contracts.
8. `FUNCTIONAL-02F` — dealer-import foundation.
9. `FUNCTIONAL-02G` — **Galeri Verification Foundation**: establish the canonical distinction between individual and Galeri sellers through a durable Galeri verification state model covering pending, verified, and rejected outcomes; keep verification evidence metadata and document references private; make transitions database-enforced and available only to authorized platform review staff; write an auditable verification-transition history; and expose only a public-safe verified signal. The foundation must provide a server-side verified-Galeri prerequisite that `FUNCTIONAL-02H` can consume without trusting profile edits or client claims. It excludes import execution, XML, dealer employees/branches, reviews, payments/subscriptions, seller-contact work, lifecycle work, and a large public/admin UI redesign.
10. `FUNCTIONAL-02H` — **Excel Import Service Boundary**: after `FUNCTIONAL-02G` is complete and its verified-Galeri prerequisite is enforced, add the server-only Excel parsing and controlled create/update/archive application boundary over the private `FUNCTIONAL-02F` bookkeeping contract. It excludes XML import and all unrelated seller, lifecycle, and commercial features.
11. `FUNCTIONAL-02I` — **Seller Contact Completion**: complete the authenticated, eligibility-gated seller-contact flow over the existing private phone facade. It excludes WhatsApp, public phone exposure, and lifecycle/edit work.
12. `FUNCTIONAL-02J` — **Lifecycle/Edit Completion**: complete the approved listing lifecycle and edit work after seller-contact completion. It is not approved for implementation before `FUNCTIONAL-02I` completes.

### FUNCTIONAL-02G acceptance criteria

- A durable canonical Galeri verification record distinguishes a dealer seller type from the verification outcome and represents pending, verified, and rejected states.
- A Galeri may submit or view only its own private verification data. It cannot grant, restore, or fabricate verified status through direct table/API access, profile updates, or client-side state.
- Only the canonical platform review authority (admin/moderator under the existing RBAC model) can make verification-state transitions; every transition is database-enforced and auditable with actor and timestamp.
- Verification evidence metadata and document references are private, RLS-protected, and excluded from public profiles, listing/search projections, and public APIs. Anonymous users and unrelated authenticated users receive no private verification data.
- Public consumers receive at most a derived, public-safe verified signal. It is produced from the protected canonical verification state, never from a seller-controlled field; no status other than verified may create a badge or equivalent claim.
- The resulting internal predicate/contract is sufficient for `FUNCTIONAL-02H` to require a verified Galeri before a service may execute an import. It does not itself parse or apply Excel data.
- Targeted role-matrix and privilege tests cover anon, individual seller, Galeri owner, non-owner Galeri, authorized reviewer, and service role; migration and security lifecycle checks pass if a migration is introduced.

## Subsequent V1 stages

1. `FUNCTIONAL-03A` — **Internal Buyer–Seller Conversations**: secure listing-bound authenticated text conversations, participant authorization, message state, block/report, safety reminders, inbox/unread state, and abuse-control foundations. Excludes voice/video, image/file/document attachments, location sharing, calls, payments, deposits, escrow, message editing, public or group chats, seller broadcasts, marketing messages, autonomous AI replies, automatic external WhatsApp handoff, and external notification delivery. Required for Web V1; high security/privacy risk; migration likely.
   - `FUNCTIONAL-03A1` — **Conversation Data & Security Contract**: create the authoritative listing-bound conversation, participant, and message model; read/unread foundation; delivery state only where the repository can define it honestly; constraints; private-by-default grants; indexes for bounded inbox/message reads; RLS/RPC boundary; server-derived buyer and seller identity; audit boundary; and any necessary database-side abuse/rate-limit state. A migration is expected. Primary gate: prove users cannot read or write another conversation.
   - `FUNCTIONAL-03A2` — **Conversation Server API**: expose the secure server-only boundary for create/get listing conversation, conversation list, bounded message list, send, and read state. Require authenticated server identity, strict request validation, safe errors, private/no-store semantics where applicable, rate-limit integration, and no message-body logging. Prefer the canonical 03A1 database contract. No migration unless 03A1 proves insufficient; no complete inbox UI.
   - `FUNCTIONAL-03A3` — **Inbox & Listing Conversation UX**: complete the normal responsive web buyer/seller text experience: start/open from an eligible listing, inbox, conversation view, send, unread indicator/count, bounded pagination/loading, empty/error states, safe public identity presentation, sold-listing history according to contract, and Turkish/English i18n. Authorization remains server-authoritative. No block/report unless necessary for safe rendering; no migration.
   - `FUNCTIONAL-03A4` — **Blocking, Reporting & Messaging Safety**: add participant block/unblock only if product contract supports it, blocked-send enforcement, conversation/message reporting, safety reminders, report-reason contract, abuse-resistant endpoints, moderation/audit handoff, reporter privacy, and no privilege escalation through reporting. No full admin moderation redesign. Migration likely only if 03A1 did not include durable safety records.
   - `FUNCTIONAL-03A5` — **Conversation Completion & Cross-System Regression**: certify 03A through the full runtime authorization matrix, inbox/message pagination, block/report, lifecycle and sold-listing behavior, seller-contact separation, privacy/logging, future-03B event boundary, accessibility/i18n, index/performance review, build/typecheck/lint, production dependency audit, trusted baseline, and final stage state update. Prefer no migration unless a genuine defect is found; no feature expansion.
   - **Required runtime security matrix:** anon is denied all conversation/message access; a buyer participant may access only their own conversation and send only when permitted, and cannot forge a seller or another buyer; a seller participant may access only conversations for their own listing in which they participate, and cannot access another seller's conversations or impersonate a buyer; cross-user access is denied; blocked sends are denied under the canonical block contract; non-participant staff are denied through ordinary user contracts; any moderation/support access uses a separately defined privileged contract; sold or ineligible listings preserve only the historical behavior allowed by product truth and never accidentally grant new contact authorization.
   - **Privacy contract:** message data is private by default. Message bodies must never be exposed through public listing APIs, search, metadata, structured data, analytics, application logs, error payloads, sitemaps, or public caches. Analytics events must not store phone, VIN, or message content. Pagination is bounded, and arbitrary participant identifiers are not exposed unless required by a safe UI contract. A voluntarily typed phone number remains message text; seller phone disclosure remains exclusively the separate `FUNCTIONAL-02I` contract.
   - **FUNCTIONAL-03B boundary:** 03A may define only safe internal durable hooks such as `message created` and `conversation unread state changed`. Web Push, SMS, email, saved-search notifications, and lifecycle notification-center completion belong to `FUNCTIONAL-03B`.

Excludes vendor-specific push/SMS, marketing automation, and campaigns. Required for Web V1; migration likely.

Excludes a general media redesign, consumer video upload, and social features. Required for Web V1; migration likely.

Excludes public fair-price claims without representative data, speculative valuation, and unapproved external market data. Required for Web V1; migration likely.

Excludes native apps, new major features, and production release itself. Required for Web V1; migration only for identified defects.

No product stage may silently introduce external providers, production changes, payment/escrow, or unapproved trust claims.
